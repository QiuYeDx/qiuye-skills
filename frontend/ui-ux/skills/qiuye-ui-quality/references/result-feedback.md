# 少量信息的结果反馈：把弹窗作为完整卡片设计

适用于导出完成、保存结果、任务已提交等信息少、下一步简单的反馈。重点是反馈层级与完整表面的构图；不要求所有弹窗使用相同外观，也不要求引入动画。

## 先选择反馈载体

- 用户只需知道动作成功、无需停下来查看或决定下一步时，优先评估已有 toast 或就地反馈；不要为了展示成功再增加一次必须关闭的模态。
- 已处于模态流程、结果需要保留供查看，或有明确的后续操作时，可以使用紧凑结果卡片。
- 多字段配置、长内容审核、重大后果确认等，仍可保留明确的标题区、滚动区与操作区。不要把少量结果信息的解法强加到这些场景。

## 失误机制

一条结果、一句重复摘要、一个关闭按钮，被直接装进通用表单弹窗：宽度沿用配置阶段，Header / Content / Footer 各自叠加 padding、gap 和边线，唯一按钮落在右下角。功能齐全，但信息显得零碎，空白远大于内容，用户需扫描多个区域才能理解一句话。

此前只检查“标题、描述、按钮都存在”，容易遗漏这个问题。验收对象应是整个表面的信息比例、留白关系和下一步，而不是组件清单。

## 完整卡片的排版原则

- 把状态标识、结果标题、必要说明、相关对象与动作作为一组构图。只在有独立信息时显示说明，不重复“导出结果 / 本次处理 1 份 / 成功 1 份”三次表达同一结果。
- 由完整卡片统一决定外部留白与内部节奏。移除无助于阅读的分隔线和重复包裹；检查最终 padding + margin + gap 的叠加，不靠多处负 margin 相互抵消。
- 宽度与信息量匹配，保留窄窗口约束；从复杂配置切到简单结果时，不机械继承宽大表单的尺寸或最小高度。紧凑不等于压小字、点击热区或阅读行距。
- 单一动作优先作为卡片底部完整的一部分：紧凑卡片可用通栏按钮，其他构图可居中或与内容对齐。不要默认套用右对齐 footer，让一个小按钮孤立在大片空白的右下角；也不要把通栏按钮推广成所有对话框的规则。
- 有两个动作时，按实际下一步确定主次与顺序；窄窗口可纵向排列。不会因“成功”就强制增加打开目录、查看列表等额外按钮。
- 单项结果可直接展示一个可识别的文件或对象。批量结果默认展示总览和详情入口；部分失败需在摘要中直接可见，不能藏到展开后才知道。长列表按需展开，失败原因和恢复入口放在相关项附近。
- 文案区分“任务已提交”与“任务已完成”；图标、颜色只是辅助，结果不能只靠颜色表达。

## 布局组件与无障碍语义分别决定

先读项目实际 Dialog 和封装源码，再判断默认样式来自哪里。shadcn 的本地副本可被项目修改；分隔线和冗余留白可能来自外层封装或调用侧，并不是使用 DialogTitle / DialogDescription 的必然后果。

- DialogHeader / DialogFooter 属于布局便利组件，不是必须保留的视觉分区。可按需省略，也可保留组件并重设边线、对齐和间距。
- DialogTitle / DialogDescription 承担标题、描述语义；可直接放进自定义卡片布局，无需嵌在 Header 中。保留它们不妨碍整体卡片设计。
- 弹窗仍须有可访问名称。无需可见标题时，采用所用库支持的隐藏标题或等效命名方式；描述确实多余时，按该库约定处理描述关联，不保留空描述、悬空的 aria-describedby 或无意义重复播报。
- 继续复用成熟 Dialog 的模态行为，包括焦点管理、键盘关闭、背景交互隔离和适当的关闭后焦点恢复。仅为去掉边线，不应改用一个缺失这些行为的定位 div。

结构示意如下；类名仅表达职责，数值与视觉应采用项目约定：

```tsx
<Dialog open={open} onOpenChange={setOpen}>
  <DialogContent className="result-card">
    <StatusIcon aria-hidden="true" />
    <DialogTitle>{title}</DialogTitle>
    <DialogDescription>{summary}</DialogDescription>
    {receiptOrDetails}
    <Button onClick={close}>完成</Button>
  </DialogContent>
</Dialog>
```

上例没有 Header / Footer，仍保留标题和描述语义。若详情会很长，可在完整表面内部划出滚动内容区，让必要动作保持可见；结构上的分区不要求绘制横线。样式变化应落在结果变体内，避免全局清除复杂表单的布局。

## 为状态间过渡留下清楚的结构

完整表面便于识别哪一个外壳在延续、哪些内容在替换，这是后续容器变形的设计基础，并非技术前提或自动获得共享元素动画的保证。保留 Header / Footer 同样可以实现动画。

在确有连续状态或已计划动效时，让背景、圆角、边框、阴影的归属清楚，并将外壳几何与内部内容变化分开。不要让重复的子表面在过渡中盖住外壳；也不必为尚未提出的动画预建克隆、测量节点或相位状态机。

需要实现时，再区分以下关系：

- 同一弹窗的配置 → 结果：可保留模态生命周期，按内容测量尺寸并编排内容交接，避免关闭重开造成遮罩与焦点闪动。
- 按钮 → 附近面板：通常是锚定位置的容器扩展。
- 卡片 → 居中详情：涉及位置迁移、布局占位、关闭回程与模态行为，不能只给整个弹窗加一个 layoutId 就算完成。

仓库中的 [Motion Recipes · Case 7：容器变形过渡](../../motion-recipes/cases/container-transform-morph.md) 详述后两种拓扑及其取舍；同一弹窗高度变化可参照 [Case 5：测量内容高度](../../motion-recipes/cases/measured-auto-height-content.md)。仅在实际动效任务中读取对应案例；独立安装本 Skill 时若这些资源不可用，不要求额外安装，也不妨碍完成静态设计。

采用动效时再验证双向与快速反向、长内容换行、文字缩放失真、关闭回程、焦点与 reduced motion；不要把案例的尺寸、时长或策略照搬成所有产品的标准。

## 验收应检出什么

- 用单项成功检查：是否一句话被重复分成几块，是否沿用空旷表单宽度，唯一按钮是否像脱离主体，圆角附近的留白是否自然。
- 用批量及部分失败检查：默认能否看懂结果与下一步，详情是否按需披露，失败是否被隐藏，展开长列表是否挤走关闭操作。
- 用长文件名、窄窗口、适用主题检查：可识别信息、换行、热区与焦点环是否保留。不能用统一缩字或裁剪来换取紧凑。
- 走一遍实际完成 → 结果 → 关闭：标题是否能被辅助技术识别，焦点是否合理，遮罩是否闪烁，背景与滚动是否意外变化。
- 保留一个复杂表单/审核的反例，确认结果卡片的局部改动没有抹掉其必要分区和操作层级。
