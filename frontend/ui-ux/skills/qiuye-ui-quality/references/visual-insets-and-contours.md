# 视觉边距与嵌套轮廓

适用于“间距看着不匀”“图标离旁边太远”“hover 后贴边”“四角空隙难看”等局部反馈，也用于新建带嵌套表面、末端按钮或浮层的 UI。目标是让内容、交互背景和外壳之间的负空间连贯；保留项目的密度、组件语义与刻意的非对称设计。

## 先把模糊反馈变成可检查的关系

| 用户说法 | 优先检查 | 不应直接推断 |
| --- | --- | --- |
| 两个图标看着离得远 | 两个可见字形之间的空白，拆开内部 padding、gap、SVG 留白 | 直接缩小所有按钮或把 gap 设为 0 |
| 灰色 hover 阴影贴着内容 | 背景表面到文字/图标可见部分的留白 | 用户一定指 box-shadow，需要加 blur |
| 左右和上下不平衡 | 靠角元素到外壳相邻两边的留白，以及弯曲段 | 全局横纵间距都必须相等 |
| 数值明明一样，角上还是难看 | 实际绘制的内外曲线、圆角压缩、背景/裁切层是否一致 | padding 相等就已完成 |
| 出现滚动条后挤了/歪了 | 实际 viewport、滚动条占位、首末项与焦点滚动 | 一律隐藏滚动条或换组件库 |
| 展开后边缘不对，收起正常 | 两种尺寸下的半径约束与轮廓层；开合中间帧 | 只给展开态换一个更大的 radius |

信息足够时先检查和修复，不要求用户提供准确术语或逐像素方案。可用“视觉间距”“背景内留白”“嵌套轮廓间距”描述结果；术语用于明确测量对象，不应变成额外审批。

## 区分四个边界

1. **内容可见边界**：图标的线条、文字字形、图片主体。SVG 的 viewBox 和透明图片矩形不等于可见部分。
2. **状态表面边界**：hover、选中或按下时的背景、边框、伪元素；用户所说的“阴影”经常指这一层。
3. **交互边界**：实际点击、触摸和键盘焦点所在的控件。可以大于图标，但不能与邻近操作争抢点击或被裁掉焦点环。
4. **外壳轮廓**：包裹它的可见容器和裁切边缘。需要明确比较的是 border 外沿、内沿还是内阴影形成的视觉边缘，并始终使用同一基准。

据此分别看：内容之间是否均衡、背景是否包得住内容、内表面到外壳是否协调。不要只量 DOM 矩形就把这三件事混为一谈。字形的精确墨迹边界难以自动测量时，DOM/SVG 几何用于定位原因，截图用于判断光学空白；抗锯齿差异不必硬凑成同一个像素值。

## 先建立关系，再分配空间

在本次工作记录中写一条足够具体的目标，例如：“底栏 hover 表面距外框两侧与底部使用同一留白，弯曲段无明显楔形空白；箭头与相邻图标更靠近，但仍留在自己的背景内。”数值从项目密度和现有参照确定，不预设统一的 6px、8px 或某一 smoothing。

- 靠同一个角的内表面，优先比较相邻两条边。曲线段观察近似法向距离/连续的负空间，不沿截图对角线机械量距离。矩形边距相等只是起点。
- 普通圆弧在同心、等距内缩条件下，可从 `内半径 = max(0, 外半径 - 内缩量)` 开始；注意边框基准。独立圆形按钮、不同曲线族和超椭圆不保证精确遵循这个关系。
- 平滑圆角要同时看基础半径、补偿半径、曲线参数和最终尺寸。两个同参数超椭圆简单缩放通常不构成严格的等距曲线，需要看最终轮廓，不宣称公式能证明审美通过。
- 若直边距离已经合适而曲线仍不均匀，先检查圆角是否被压缩，不盲目加大 padding 或整个面板高度。
- 同一轮廓的背景、玻璃材质、边框与裁切层应共享形状定义；只让一层变平滑会产生漏色、缺口或视觉上的双重轮廓。
- 调整父级内边距后，复查通栏负 margin、底栏、折叠区和消费页覆盖；不要靠多组相反偏移偶然抵消，也不要为展示圆角额外套装饰卡片。

### 矮控件与分角设计

矮按钮放不下上下两组大圆角时，浏览器会缩小实际半径；computed style 仍可能显示原来的值。检查**进入 CSS 的最终半径**，不要只看组件的基础 radius。普通圆角先比较左右两侧的纵向半径和与高度、上下两侧的横向半径和与宽度；百分比需按对应轴换算。

修复由轮廓职责决定：

- 底部操作仅下两角需要贴合外壳时，可保留下角、减小上角；顶栏则反过来。不是所有按钮都需要四角相同。
- 四角都承担对称造型时，可降低平滑度/半径，或使用已有尺寸感知实现；不要默认将它改成非对称角。
- 只有操作密度允许时才微调高度。装饰背景与热区分层也可行，但仍需验证裁切、相邻按钮与焦点。

标准圆弧的半径约束见 [CSS Backgrounds §4.5](https://www.w3.org/TR/css-backgrounds-3/#corner-overlap)；其他 corner-shape 还应核对实际浏览器与相应形状的约束。这里的半径和检查是故障定位线索，不是所有曲线的完整求解器。

## 移动内容时，连同 hover 表面一起设计

图标之间的视觉空白可能来自：图标内部空白 + 控件 padding + 控件间 gap + 相邻控件 padding。先找到多余空间的来源，再决定改哪一层。

- 调整图标位置后，立即打开 hover 和键盘焦点，确认背景仍自然包住内容。不能只做 translate，让箭头贴在背景边缘或漂到热区外。
- 有空间时可同步重新分配按钮宽度、内部留白和相邻 gap；背景也可用独立层调整，但不遮盖邻近操作，不改变其命中顺序。
- hover 不应通过临时增加 padding/border-width 引发布局跳动；状态表面的几何范围提前确定。高频扫描列表的颜色反馈应及时，遵循用户已有的即时反馈偏好，不为统一动效而强加延迟。
- 同时看未悬停、hover、focus-visible 和选中旁的 hover。不能靠去掉可访问焦点或全部背景来藏住问题。

## 滚动是布局的一部分

先确定真正滚动的 viewport，以及滚动条是否占据内容宽度。对照短列表和溢出列表，观察文字、末端图标与 hover 背景是否横向跳动或被覆盖。

| 选择 | 适用判断 | 必须复验 |
| --- | --- | --- |
| 原生滚动条并预留空间 | 长内容/拖动定位重要，产品允许占位 | 平台差异、需要时的稳定 gutter、两侧视觉平衡 |
| 自定义/悬浮滚动条 | 需要统一样式或控制位置 | 不压住文本、选中边缘和操作；实际 viewport 的 ref/事件正确 |
| 隐藏滚动条 | 用户认可简洁呈现，且当前任务不依赖拖动滚动条 | 滚轮、触摸、键盘与当前项定位保留，渐隐/部分下一项等提示能表达可继续滚动 |

没有通用最优方案。不要为一次边距修复必装 ScrollArea，也不要把本项目接受的隐藏滚动条推广为全站规定。渐变遮罩只在相应方向还有内容时出现，不能永久遮住首末项或焦点提示。

自定义滚动条同样可能破坏几何：绝对定位的条若已经用 top/bottom 限定位置，再叠加满高和纵向 margin，可能产生额外 overflow。`overflow:hidden` 的祖先仍可能被焦点程序滚动。用 Home/End 或最后一项焦点复验，查看是哪一层 scrollTop 变化；修真实尺寸，不用每帧归零滚动来掩盖问题。

## 验收应能暴露这次的缺陷

针对受影响对象选择状态，不要求全站穷举：

- 靠角处真实 hover，首/末项与选中项旁的 hover；不能用未 hover 截图替代。
- 短/长内容，有/无溢出；最窄受支持布局，必要的主题和普通圆角 fallback。
- 轮廓会变形时检查展开、收起及中途反向；玻璃/边框/裁切仍贴合。
- 键盘进入、Home/End 或末项聚焦后，再测左右/底部空白；实际点击确认改位置后命中正确。

尺寸以同一稳定帧、同一 CSS 坐标系测量；有 transform 时，不把变换后的矩形尺寸直接用于未变换的 radius 约束。允许项目合理的亚像素误差，曲线与内容的光学均衡还需实际看图。已有 [渲染验收方法](rendered-review.md) 提供测量入口。

完成记录应能说明：哪个边界不均衡、由什么层级/规则造成、改了哪一层、哪种真实状态验证了它。只有代码与数值检查时，明确尚未完成视觉验收；不要报告“等距断言通过，所以所有圆角都已美观”。
