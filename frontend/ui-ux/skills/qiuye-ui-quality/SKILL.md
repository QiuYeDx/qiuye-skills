# UI 质量与自主验收

目标是把用户反复指出的可发现问题，提前转化为设计约束、真实状态样本和交付前修复。首版实现之后还要有一次以找问题为目的的审查；没有问题时不为“迭代”制造改动。

## 先确定适用范围

- 新建界面：从实际用户、主要任务与使用频率选择布局和视觉方向。没有现成设计时可自主确定合理方向，不必让用户审批每项细节。
- 现有项目：优先遵循明确用户要求、项目设计约定和当前受认可的同类界面。“像 Apple / Vercel 一样专业”通常是质量目标，不自动授权搬入它们的外观。
- 局部修复：检查目标组件、关联状态和同源问题；不要自动重写全站。用户要求统一多个页面时，才把这组页面作为验收范围。
- 纯建议或只读评审：交付证据、问题与建议，不把本 Skill 当成修改授权。

本 Skill 管交付过程。项目级 Skill 管品牌、组件与数值。专门的动效、可访问性或前端故障 Skill 仅在任务需要时加载；本 Skill 不要求额外依赖、全套 Spec 文档或多 Agent。

## 1. 在写样式前建立参照

对已有产品，阅读目标页面、相关共享组件及主题样式，并在可用的运行环境中观察最接近的已认可界面。页面重写通常需要一处同类页面和一处共用组件作为参照；小修复只需要直接相关的参照。

用简短工作记录明确以下内容，不必生成独立设计文档：

| 项目 | 要明确的事实 |
| --- | --- |
| 用户任务 | 主要操作、典型规模、重复执行成本、需要扫描或比较的信息 |
| 视觉依据 | 参照页面、色彩与排版 token、密度、边框和圆角层级 |
| 组件来源 | 实际组件文件及 variant / size / shape，不能只写“使用某组件” |
| 空间关系 | 哪些边缘、列和基线应共享参照，哪些间距同类，哪些留白服务于分组 |
| 验收样本 | 真实内容与合理规模、主要状态组合、会改变结构的状态转换、适用窗口 |

没有运行环境时先做代码和截图参照分析，但不要把它写成已完成的运行验证。参考截图中的批注和示例内容是证据，不是额外操作授权。

## 2. 先设计关系，再选数值

- 先确认信息层级和工作流，再调颜色、阴影、动效。操作型工具应让主要工作区域可见，避免把文件元数据、空状态或装饰区做成主视觉。
- 检查方案在实际规模和重复使用下是否仍然顺手，明确操作对象与作用范围。用足以暴露操作成本的样本判断必要能力，不因存在列表就默认增加整套管理功能。
- 分别检查纵向预算与横向利用：标题、上传区、元数据、Tab、表头和分页各占多少高度，剩下能显示多少有效内容；是否一边反复叠行、一边横向大面积空闲。不能只检查“没有溢出”。
- 沿用项目的间距尺度。区分面板外间隔、内部留白、字段间距和控件热区；“一致”是同类关系一致，不是所有数值相等。
- 圆角附近单独检查等距关系：靠角的按钮、输入框或嵌套表面，到外层容器相邻两条内边界的留白应优先相等，例如右上角比较上/右，右下角比较下/右。统一 token 不代表最终等距；还要检查内外圆角形成的空白是否自然，不能一侧贴边、一侧松散。该原则用于靠角包裹关系，不要求整页所有水平/垂直间距相等。
- 对齐到真实内容边缘：按钮外框、图标字形、焦点轮廓不是同一个边界。需要说明光学调整时保持同类控件一致，不靠压缩点击热区来求整齐。
- 不等边距先判断哪个值合理，再统一相关区域；不要总把较小边距增大到较大值。局部看齐可能让整页更松散，并与邻近面板继续不一致。
- 给内容列 `min-width: 0` 等收缩条件。普通列表项按正常一行排版，多行只增长当前项；比较型行里的编号、时间、内容和操作保持顶部基线关系。
- 明确字符截断策略。文件名常需要首尾信息及完整名称入口；正文和错误信息通常应可换行。不能把所有字符串统一末尾截断。
- 复用共享组件的实际呈现层。检查默认值与调用侧覆盖的最终组合，包括 Tooltip 的换行、Tab 的形状和表单的尺寸。
- 同一对象的多个状态要有清楚的视觉优先级，避免重复强调或互相竞争；独立语义与键盘焦点仍应可辨认。操作入口按频率、关联性与影响组织，简洁不能以牺牲可发现性为代价。

在实现相关组件前，阅读 [常见失误与修复](references/failure-catalog.md) 中对应的条目。那里给出故障机理与验收对象，不提供通用像素配方。

### 少量信息的结果反馈

简短结果需要独立模态时，优先把它作为完整卡片设计：统一留白与信息层级，避免照搬表单的多段边线、叠加 padding，以及孤立在右下角的单一按钮。Header / Footer 是可选布局，Title / Description 的语义职责另行保留；复杂表单仍按实际任务分区。相关设计与验收见 [结果反馈卡片](references/result-feedback.md)，其中也说明与后续容器变形过渡的关系。

## 3. 用真实状态完成初版

让状态模型进入布局，而不是事后补上：

- 覆盖本任务涉及的主要操作、等待、成功、失败与恢复路径；检查用户能否理解结果并找到适当下一步，保留业务行为与已有授权边界。
- 至少准备正常内容及一种能暴露布局弱点的内容。表格要有相邻短行和多行；文件列表要有可区分的长短名称；国际化页面要有实际长文案。
- 控件用符合语义的组件：切视图与选参数不能混用，箭头方向和操作文案要能同时被理解。不要为统一“上传/下载”而改变实际本地处理或网络行为。
- 悬停、键盘焦点、选中、禁用和展开是不同状态。特别检查选中项旁边的悬停项、真实打开的 Tooltip、Tab 切换后的尺寸和窄屏换行。
- 除单独状态外，还要检查同一对象可能同时成立的状态，以及会改变结构的关键转换。根据任务选择样本，不要求穷举所有组合。

## 4. 切换到审稿视角

完成初版后暂停继续添加功能，按以下次序检查并记录具体问题：

1. **方向**：与本产品相邻界面放在一起，是否像同一套产品？主要任务是否易于找到？
2. **结构**：信息层级、空间分配、列表密度是否合理？有没有被挤走的工作区？
3. **细节**：比较同类边距、靠角元素到相邻两边的等距留白、内外圆角轮廓、基线、图标与按钮、相邻状态、文本截断和 Tooltip 的实际外框。
4. **交互**：执行真实操作、键盘导航和相关恢复路径；比较状态转换前后，检查工作区、下一操作目标、滚动锚点和焦点是否受到不必要的扰动，任务是否有清楚去向。
5. **适配**：检查目标窗口和语言中的换行、溢出、滚动、遮挡与主题。

同时使用渲染截图和必要的 DOM / computed-style 测量。测试通过只证明断言覆盖的性质；“截了图”不等于“看过图”，打开 Tooltip 的测试也不等于检查过其留白。

具体的取样、测量和证据方法见 [渲染验收方法](references/rendered-review.md)。不要把自评成“高级、美观、无问题”当作证据。

## 5. 修复、复验与收敛

- 修复可观察的最高优先级问题，先方向和结构，后局部细节。用户指出同类问题第二次出现时，回看共同的组件、布局约束和测试缺口，不能只增加新的局部覆盖。
- 每个问题记录为“状态/位置 -> 现象 -> 原因 -> 改动 -> 复验”。简单任务可保存在工作记录中，大任务沿用项目已有记录位置。
- 检查同一原因在已授权范围内的其他实例。共享组件变化要验证真实消费页及不同 variant，并修正配套的负边距、分隔线、底栏和局部覆盖。
- 修复后重看受影响的真实状态。已通过的检查不因仪式感重复运行；只有新改动、失败或尚未解决的风险才扩大验证。
- 结束条件：本次范围没有已知且能处理的视觉/交互缺陷，相关行为检查通过，最终截图已审阅，证据对应最终代码。没有缺陷时无需强制做第二次代码改动。
- 缺少凭据、平台、真实数据或运行能力时，完成独立可验证部分，明确剩余限制；不要反复重试不变的阻塞，也不要让用户逐像素指挥可自主解决的细节。
- 清理本次启动的预览、前端服务和测试实例，遵循项目已有进程规范。不要关闭用户原有窗口。

## 验证按影响范围选择

| 改动 | 通常足够的证据 |
| --- | --- |
| 一个 Tooltip 或间距问题 | 目标组件的长短内容、有关交互状态与窄边界；有必要时量尺寸，无需全站回归 |
| 页面重写 | 项目参照对比、主要工作流、典型及异常内容、目标窗口与主题；功能检查加截图复查 |
| 共用组件 | 消费者清单、相关变体、代表性组合和受影响页面的布局检查；复杂组合按风险补充 |

可复用的几何或交互约束值得保留测试；不要为一个可逆 CSS 微调写只匹配类名的测试，也不要用庞大测试数量代替针对性证据。

## 交付与维护

简述具体体验改善、验证范围、实际限制以及已知剩余问题，不用“完美”概括未覆盖状态。可附少量最终截图，不把内部检查清单塞进产品界面。

新的反馈先追问原验收为何遗漏，再补能检出该类问题的决策提示或证据方法。通用方法放入对应故障条目；项目数值、组件、业务流程和具体事故记录留在项目 Skill。不要把单个产品的解法或审美偏好积累成全局规则。

需要评估本 Skill 的适用边界与决策质量时，使用 [行为评估场景](evals/scenarios.md)。场景预期不等于已证明任意模型都能首轮通过。
