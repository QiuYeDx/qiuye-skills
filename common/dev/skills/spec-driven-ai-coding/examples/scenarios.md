# 行为场景：预期做法，不是已测模型成绩

## 小修改

用户明确调用本 Skill，只修改一个按钮的尺寸，沿用现有 token。
正确做法：读相邻组件与项目约束，简短说明改动和验收，局部修改并验证实际影响；通常走 S。
不要创建 BRD、模块目录、五态空表，也不要为无关后端设计填写“不涉及”。

## 正确 AC 下的 bugfix

既有 AC 规定“导出筛选后的记录”，实现导出了全部记录。
正确做法：复现并关联 AC，补能失败的回归验证，再修实现；需求不变。必要记录归根因/代码变化，不编造需求新版本。
如果用户改为要求“导出全部记录”，则是外部行为变化，应明确修改需求并确认影响。

## 一文件高风险

一处接口漏了资源归属检查。
正确做法：规模可为 S，风险 high。保留语义正确的 AC，确认授权/安全边界，增加跨用户访问反例及合法访问回归。
不是自动写全套 L，也不是因为一行代码就忽略权限风险。

## 性能未知

无法仅靠文档判断某 Canvas/WebGL 方案能否承受目标数据规模。
正确做法：先用隔离实验比较少量候选和固定合成数据，记录测量条件与实际结果；再选择方案。
不要先给所有模块写确定性能承诺，也不要把 benchmark 演示代码当成正式交付。

## UI 已实现但没有浏览器

本任务 required 中有浏览器交互验证，而当前宿主无法启动浏览器。
正确做法：运行能运行的类型/组件检查，列出浏览器步骤尚未执行，标待验证/阻塞。
不能把 browser 项改 na，也不能写“观察到空态正常”，更不能让 checker 绿灯替代真实验证。

## 并行共享文件

两个 Agent 分别做不同模块，但都需要改路由入口或锁文件。
正确做法：协调负责人指定单写者、拆分任务或串行；其他 Agent 维护各自真实写集与分支证据。
不能认为“模块名不同，所以不存在冲突”，也不能将不同分支的自我领取当成锁。

## 已批准的连续任务

用户要求完成已确认的当前增量，T-APP-01 完成后 T-APP-02 的依赖已在当前基线可用。
正确做法：更新证据后继续下一个任务，不强迫用户再说“继续”；同一时刻只持有一个任务。
出现范围/权限变化或必要验证不可执行时按边界停止，报告已有结果和具体缺项。
