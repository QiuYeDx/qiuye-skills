# 接口与数据质量：按实际契约使用

## 设计

记录相关请求/响应类型、输入校验、访问策略、错误语义、状态迁移和数据约束；优先引用项目已维护的 Schema/OpenAPI/类型文件。
公开接口应明确允许匿名，而不是强制登录；私有资源检查实际授权/归属，不把“已登录”当作全部权限判断。
数据模型只写相关字段/索引与变化；事务、并发、幂等、分页、批量上限、超时重试按接口语义决定是否适用。
不要把每个写操作都强行设计为客户端无条件幂等，也不要为本来没有列表的接口添加分页。

## 实现

遵循现有分层，不重建整个架构。输入不可信，授权在服务端执行；参数化查询；敏感信息不进入不必要的日志/响应。
事务边界和一致性策略明确；依赖数据库约束时与应用逻辑一致。配置遵循项目方式，不硬编码密钥。
错误包含可定位上下文，不吞异常、不用固定成功结果掩盖失败；日志遵循项目规范。
需要观测性能时写测量数据规模与环境，不凭空宣称吞吐/延迟已达标。

## 验证

运行本任务适用的正常、非法参数、匿名/无权限、跨资源访问、不存在、重复/并发和极限值测试。
写操作核对数据结果与状态迁移。mock 的测试用于本层逻辑，真实服务/数据库一致性由适用的集成验证承担。
无真实后端时，前端或契约测试可完成局部工作，但端到端任务不得据此宣布完成。
局部任务跑针对性测试，模块/集成阶段补必要全量回归，遵从项目原有 CI 门禁。

## 迁移与恢复

迁移仅在隔离、可丢弃数据库或明确授权环境验证。记录向前升级、旧数据兼容、恢复/回退策略。
并非每个迁移都有安全 down 脚本：不可逆变更要明确备份恢复或 roll-forward 方案，不能编一个会丢数据的“可回滚”。
线上执行、恢复备份、删除数据和发布仍需独立授权；设计 approved 不能替代操作许可。
