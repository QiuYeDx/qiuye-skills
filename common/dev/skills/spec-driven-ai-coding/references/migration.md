# 安装替换、旧项目兼容与 M→L

## 安装新版不等于迁移业务项目

在 qiuye-skills 中，用整个新版 `spec-driven-ai-coding/` 替换 `common/dev/skills/spec-driven-ai-coding/`，不要仅覆盖 SKILL.md 后混用旧脚本/模板。
先保存未提交改动并把旧目录移到 skill 扫描目录之外；新旧同名 Skill 不要同时放在自动发现路径。
仓库根 README 的介绍/目录需由维护者同步，参考包内 integration-notes.md。本包不修改你的远程仓库。

## 继续旧版项目

v1 的需求、tasks 台账和旧格式 final_design/execution_plan 可继续作为权威来源。新 Skill 的风险、变更分类、真实验证原则仍适用。
v2 checker 只接受有 spec.json 的 v2 格式；拒绝旧结构是显式边界，不是证明旧文档有错。
需要机械门禁时才选择迁移，不能声称“新版与旧版脚本完全兼容”。不运行脚本时也要明确是人工审查而非 checker 已通过。

## 选择迁移 v1

先固定一个基线分支/提交并暂停并行编辑，保留旧文档和验证证据。
只转换当前活跃需求：保留 BR/R/T ID 与来源，将原任务台账和任务详情合并为一个任务块；重复/冲突编号先人工核对。
把每条现有 AC 编号，不能趁迁移改用户期望；将明确不在当前增量的需求标 deferred 并保留路线图。
生成 spec.json，明确当前批次和真实历史批准来源。无法找到的批准标 pending，不从“已有代码”推断用户已批准。
把已完成任务的现有证据整理为 record，能核对版本与结果才保留完成；无证据标待验证，不能伪造回填测试通过。
旧 overall 移到 spec 根内的 `legacy/` 或项目既有归档目录；检查并更新引用，再生成新只读总览。
跑 draft→修结构→ready→复核批准→重新执行必要验证。记录迁移映射和未解决项，审查后才采用新台账。

## M→L

脚手架不会在同目录自动升级，也不提供覆盖参数。
暂停并行编辑、保存基线；在同一 Spec 中将现有三件套移动到一个实际模块路径，保持 code/ID；创建 BRD 表达真实业务目标并映射现有 R 来源。
新增确有必要的模块，不默认创建 common；修改 spec.json 的 tier/modules，补业务目标与当前批次的批准，原批准失效时重新确认。
移动后的 record 路径仍相对 Spec 根，通常不用改变；旧模块内的相对代码/文档引用要核对。需求身份变化会影响指纹，不重新跑测试时不可机械复制新 hash 冒充复验。
不要在 L 根目录残留 M 的 requirements/design/tasks：checker 会拒绝这种混合结构，避免悄悄忽略旧内容。
先生成总览预览，核对 BR→R→AC→T 覆盖与依赖，再切换权威入口。

## 新增模块/切换批次

手工或由 Agent 按模板建立新模块目录，并在 spec.json 声明唯一 slug/code/path。检查器会检测漏登记目录。
新增批次必须有独立 approval/acceptance pending，不能复制旧批准值。当前完成不代表未来批次获得批准。
对已验收功能的改变优先追加新需求/新任务并记录 supersedes 关系于文字，保留历史记录；不要为了“最新文档整洁”抹掉历史证据。
