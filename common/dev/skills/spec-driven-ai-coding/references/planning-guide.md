# 分流与滚动规划

## 先看事实，再问问题

读取项目指令、相关实现、最近似功能、测试入口、构建命令与数据边界。先查 README/package 配置/接口定义可回答的问题，不要求用户重复讲仓库已有事实。
已有图表、组件库、表格或状态管理约定时指出具体文件，复用优先于重建。
只问影响需求/风险且无法从允许来源回答的阻断问题，批量给出推荐方案与影响，避免把全部技术决策推给用户。

## 规模不是风险等级

| 任务 | 规模示例 | 另行判断 |
| --- | --- | --- |
| 十多个文件内的机械重命名 | S | 看是否改公共 API、是否有自动化回归 |
| 一处资源归属校验修复 | S | high：越权反例、边界验证、具体批准 |
| 新增一个带保存接口的设置功能 | M | 跨前后端并不自动升 L |
| 一个全栈导出功能，分为筛选、CSV、异步队列三期 | L 或先做 M | 多期交付与依赖才是拆分依据 |
| 不清楚某 Shader 的实际性能 | 原规模 + spike | 技术未知不等于需求庞大 |

S 可只用对话计划；M 默认三份短 Markdown + spec.json；L 只多出粗粒度 BRD 和所需模块。
升级时保留原 ID 和来源，不因结构变化重新编造需求。不要仅为了达到“一任务≤300行”打断可验证增量。

## 需求写到什么粒度

需求描述可观察行为，不把所有内部算法和类名写成产品承诺。
每条当前 R 至少一条稳定 AC；必要边界可单列 AC，例如失败保留输入、无权限拒绝、空集输出、重复提交。
明确本次不做什么。性能目标需附来源/测量条件；未知可以写待测假设，不能凭空承诺“P95 500ms”。
非阻断且可逆的 UI 微文案、内部命名、沿用项目默认值，Agent 可自行决定并在设计/记录解释，不需全部变成 A-xx。
影响产品范围、权限、数据语义或不可逆结果的假设放 spec.json decisions，写影响批次与 blocking。

L：BRD 表达目标与业务边界，R 细化具体行为。公共技术任务可以关联它支持的真实 BR/R；不要为了给基础设施找编号，发明用户未要求的新业务功能。
任务追踪应覆盖当前 AC，而不是仅仅在文本任意位置出现一次 R 编号。

## 滚动窗口

当前批次要求 active 的 BR/R、有可实施设计和任务。后续批次可以只有 deferred 的 BR，模块尚未拆分时不必创建空目录。
已有未来模块目录时允许简短需求/设计及空 tasks.md；只有成为当前 active 批次后才补足细节。
不是“未来不规划”，而是先规划目标与关键依赖，临近实施才规划不稳定细节。
每期至少交付一条可演示链路。避免先做完整数据层/完整前端/所有 common，再首次端到端验证。

## 可行性实验

用 templates/spike.md 约定问题、可判定结果、范围、临时代码位置、数据与副作用许可。
允许在批准的隔离工作区写实验代码、构造合成输入、测性能。不得借“实验”绕过生产数据、部署、网络或依赖安装权限。
无法在当前环境验证时明确剩余未知，不凭想象收敛方案。实验结论进入设计；实验通过不等于正式 AC 已完成。

## 文档预算

只保留恢复开发与验证所需的信息。M 的短文档可以各只有几个小节；不强迫套满旧版十二节设计。
跨模块契约引用现有 OpenAPI/Schema/类型文件的路径和版本/变更，不抄成多个“唯一真相”。
已存在且可靠的组件规范、token、接口错误约定用引用，写本次差异。中文界面不意味着协议枚举、错误码和所有日志都改成中文。
