# 规划指南

供规划者在阶段 0–2 使用：怎么问需求、怎么写 BRD、怎么拆模块、怎么拆任务、存量项目怎么调研。

## 需求梳理问题清单

分批提问，每轮 ≤6 个，先问阻断性问题（不知道答案就无法写 BRD 的）。已在用户描述中明确的不要重复问。有 AskQuestion 类工具时优先使用并给出推荐选项。

目标与成功标准：

- 这个需求解决谁的什么问题？不做会怎样？
- 上线后用什么指标或现象判断成功？
- 最小可用版本包含什么？哪些可以放到下一期？

用户与角色：

- 有哪些用户角色？各自能做什么、不能做什么？
- 是否有管理员/审核/只读等特殊角色？

核心场景：

- 用户最常走的 1–3 条主流程是什么？请按步骤描述
- 每条主流程中，哪一步最容易出错或最需要提示？
- 有哪些异常情况必须处理（空数据、无权限、网络失败、并发冲突、数据超限）？

范围与边界：

- 明确不做什么？
- 与现有功能的关系：替换、并存还是扩展？
- 是否涉及历史数据迁移或兼容？

数据与接口：

- 涉及哪些核心实体？关键字段与约束？
- 是否依赖外部系统或第三方接口？可用性如何？
- 数据规模预估（条数、并发、文件大小）？

前端与体验：

- 有设计稿或参考产品吗？没有的话希望什么风格与密度？
- 目标设备：桌面、移动、都要？最小支持的屏幕宽度？
- 沿用项目现有组件库和设计 token 吗？

非功能：

- 性能、安全、权限、审计、国际化/语言要求？
- 部署环境与技术栈约束？

协作与节奏：

- 是否多人/多 Agent 并行开发？如何分工？
- 代码注释与 UI 文案语言（中文开发？）
- 检查点习惯：每个阶段都确认，还是只确认 BRD 与最终验收？

退出条件：能写出带验收要点的 BRD，且没有阻断性未决问题。其余未决问题编号 `Q-xx` 带入 BRD。

## 用户说「由 AI 自行补充细节并设计方案」时

1. 先列出你打算补充的决策点（通常是：字段细节、异常处理策略、UI 布局与文案、默认值、边界值）
2. 有条件时联网调研 1–3 个同类产品的做法，在 `discovery.md` 记录来源与结论
3. 每个决策写成 `A-xx` 假设，进入 BRD「约束与假设」章节，标注「待确认」
4. 选择最保守、最可逆、最符合项目现状的方案
5. 在 CP1 用一张假设表请用户批量确认，而不是逐条打断

## BRD 写作指南

BRD 是唯一需求基底。写作顺序：

1. 先写「范围外」，再写「范围内」——先划清边界，防止蔓延
2. 按用户角色 × 主流程枚举功能点，每个功能点一条 `BR-xx`
3. 每条 BR：标题、描述、优先级（P0/P1/P2）、涉及角色、验收要点（3 条以内，可测）、备注
4. 主流程与异常流程用编号步骤写，每步写「用户做什么 → 系统做什么 → 用户看到什么」
5. 非功能需求给数字
6. 约束与假设：技术栈、现有系统、语言约定、`A-xx` 列表
7. 模块划分草案：见下节
8. 未决问题 `Q-xx`：问题、影响的 BR、谁能回答、默认方案
9. 文档头部维护版本号与变更记录表；每次变更管理升版本

存量项目额外写「现状与集成点」：相关文件路径、已有接口、已有表、可复用组件、已知坑（引用项目 pitfall guard）。这一节靠读代码得出，不靠猜。

## 模块拆分原则

拆分维度（按优先顺序选一个主维度）：

1. 业务领域：用户、订单、支付、报表……（领域清晰时首选）
2. 页面群：一组紧密相关的页面 + 其后端接口（面向前端为主的需求）
3. 服务边界：已有微服务或明确的部署单元

规则：

- 模块数量：L 需求通常 3–7 个（含 common）；超过 7 个考虑合并或分期
- 每个模块能被一个 Agent 独立开发，与其他模块只通过 `module-common` 声明的契约交互
- 模块内高内聚：一条主流程尽量落在一个模块；必须跨模块时，接口契约先进 common
- 每个模块写清「职责」「不负责」「依赖的 common 契约」「代码落点」
- 模块短码 `<MOD>`：大写、无连字符、≤8 字符（`AUTH`、`ORDER`、`REPORT`）

`module-common` 收纳：

- 共享领域模型与类型定义
- 接口约定：统一响应结构、错误码表、分页参数、鉴权头
- 权限点定义与角色矩阵
- 公共前端组件、布局、主题 token、工具函数
- 公共后端基础设施：中间件、异常处理、日志、配置
- 语言约定与文案规范

common 不收纳具体业务逻辑。common 的任务在阶段 0 完成，其他模块依赖它。

## 任务拆分原则

- 粒度：一个会话可完成（新建/修改 ≤8 个文件或 ≤300 行有效变更）；做不到就继续拆
- 每个任务是一个可验证的增量：完成后有可运行的测试、可访问的接口或可打开的页面
- 顺序：
  - 阶段 0：common 契约、基础设施、公共组件
  - 阶段 1：最小端到端链路——选一条 P0 主流程，从表到接口到页面打通
  - 阶段 2+：按优先级横向扩展其余 BR
  - 最后：打磨（性能、动效、文案统一、可访问性）
- 前后端解耦：接口契约进 design 后，前端任务可用契约 mock 并行开发，但合并前必须对接真实接口并删除 mock
- 每个任务写：目标、关联需求、依赖、涉及文件、实现要点、验收标准、测试要求
- UI 任务的验收标准固定包含「五态齐全，浏览器自检通过」；接口任务固定包含「正反例通过，错误码符合契约」
- 不要把「写测试」单独拆成任务；测试属于每个任务的测试要求

## 存量项目调研清单

在写 BRD「现状与集成点」和 design「现状与约束」前完成：

- [ ] 读项目 README / AGENTS.md / CONTRIBUTING / 已有设计文档
- [ ] 读项目级 pitfall guard（若存在 `.agents/skills/*-pitfall-guard`）
- [ ] 确认技术栈、包管理器、构建/测试/lint 命令
- [ ] 找到与本需求相关的现有页面、路由、组件、接口、表、服务，记录路径
- [ ] 确认项目分层与命名约定（目录结构、文件命名、组件命名、接口风格）
- [ ] 确认设计系统：组件库、主题 token、图标库、动效库
- [ ] 确认权限模型与鉴权方式
- [ ] 确认错误处理与响应结构约定
- [ ] 确认语言约定（注释、文案、日志）
- [ ] 找到最接近的已有功能作为实现参考，记录具体文件
