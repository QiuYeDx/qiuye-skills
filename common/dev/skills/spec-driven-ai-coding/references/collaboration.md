# 多 Agent 协作：先验证隔离条件，再选择并行

## 默认串行；并行不是 L 的必选项

先确定当前端到端增量和依赖。只有任务契约足够稳定、实际写集可隔离、运行环境不会互相污染时才并行。
同一个 Agent 可以连续完成多个任务；同一时刻只持有一个活动任务。交接不能只靠聊天上下文。

## 最小协调协议

指定一个集成/协调负责人，为每个任务分配负责人、工作树/分支和起始代码基线。
协调负责人是任务领取和集成的权威点；禁止多个会话在离线分支自认已经原子领取同一任务。
共享工作树内直接修改 tasks.md 不是互斥锁；不同 Git 分支也没有跨分支锁。必须通过可见协调消息/现有任务系统确认后领取。
没有协调条件时串行，不自行构建一套调度服务。

## 用真实写集判断冲突

写集用仓库根相对文件或目录前缀，包含测试、配置和生成文件；不只写抽象模块名。通配符不用作机器检查边界。
典型共享资源：package/锁文件、路由注册、Schema、迁移序号、主题 token、CI 配置、开发服务端口、测试数据库。
共享文件在 spec.json parallel.shared_files 指定单写者。其他任务只提接口需求或补丁建议，不直接改。
公共契约由业务所属模块维护并提供稳定引用；真正共享的能力才放 common，不默认把全部业务模型迁进 common。

## 台账与总览

各模块 tasks.md 是唯一任务状态来源。模块 Agent 维护自己的任务块，协调者负责合并这些源文档。
spec.json 的批准/批次/分工由协调者维护；Agent 不各自更新总表。task-list-overall.md 合并后统一生成。
同一文件有冲突先核对真实进度，不简单选 ours/theirs 覆盖其他 Agent 的状态。
检查器只看到当前文件快照；它不能发现另一个尚未同步的分支，也不是分布式锁。

## 依赖必须实际可用

依赖已完成不等于已合并。开始下游任务前确认依赖提交在当前基线，或明确验证当前共享工作树含对应实现。
在「依赖确认」写每个依赖 ID、提交/快照与核验动作；必要时使用项目已有 Git/CI 工具验证，不能只看状态。
「集成版本」记录集成后的提交/快照，不能填写尚未创建的 hash。checker 只检查声明，不能证明 Git 祖先关系。

## 合并与验收

集成负责人按依赖顺序合并，处理契约和生成文件冲突，在合并版本上执行跨模块验证。
局部任务可能已完成但批次仍未验收；不同分支上的绿测试不能合成为集成结果。
出现共享变更时重新计算影响与写集；涉及需求/权限/兼容承诺变化重新确认。
临时端口、测试数据集、环境变量命名也需隔离，避免一个 Agent 重置另一个的验证环境。

## 边界

v2 脚本能发现已同步任务的活动写集冲突、共享写者违规和未完成依赖；不能自动调度 Agent、创建 worktree、持有锁或合并代码。
