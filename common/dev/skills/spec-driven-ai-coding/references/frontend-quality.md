# 前端质量：设计先行，渲染审查后交付

涉及页面、组件、样式或交互时，在写相关前端代码前读取本文件。S/M/L 都保留设计与渲染审查，按影响面缩小内容和验证范围。纯类型、纯服务端逻辑且不影响 UI 时无需此流程；纯文案也要检查受影响排版，可沿用已有设计。

## 1. 选择设计依据与可用 Skill

先遵循明确用户要求、项目设计约定和当前受认可的同类界面。读取目标实现、共享组件与主题 token；运行条件允许时观察最近似的页面。没有运行环境时可先分析代码或已有截图，标明哪些判断尚未经运行确认。

- 当前环境有适用的前端/UI/设计 Skill 时，读取并使用与本任务匹配的流程。`qiuye-ui-quality` 适合设计基准、视觉一致性与渲染审查；项目级 Skill 提供品牌、组件和具体数值。记录实际使用的名称/路径及有关决定，仅提及名称不算已使用。
- 动效、可访问性、CSS 故障等专门 Skill 仅在本任务需要时读取，不一次加载所有前端 Skill；纯审计 Skill 的建议不能冒充已实施修复。
- 没有合适的已安装 Skill 且可联网读取时，可参考 [qiuye-ui-quality](https://github.com/qiuyedx/qiuye-skills/tree/main/frontend/ui-ux/skills/qiuye-ui-quality)，先读其 `SKILL.md`，再按当前问题读引用资源。远程内容随仓库演进，记录实际读取来源；本流程不依赖全局安装。
- 无法读取外部 Skill 时，直接执行本文件的设计与审查闭环。已有项目至少沿用同类页面的视觉语言和真实组件变体；新项目依据目标用户与主工作流自主确定一致的视觉基准，不将缺少 Skill 变成停止设计的理由。

## 2. 写前端代码前完成设计基准

M/L 写入当前 `design.md`，S 可只用简短工作记录。已有规范可引用具体位置并说明本次差异，不另建重复设计台账。

| 设计项 | 实施前要确定的内容 |
| --- | --- |
| 用户与流程 | 目标用户、使用频率、入口、首要操作、主流程和失败恢复；数据来自哪个真实契约 |
| 视觉参照 | 同类页面/截图与实际代码位置、字体/色彩/间距/圆角 token、密度；无现成参照时说明自主选择的依据 |
| 布局与空间 | 信息层级、主要区域和操作位置、对齐与分组、有效工作区的纵向预算及横向利用、窄屏重排和滚动归属 |
| 组件与状态 | 复用组件的文件及 variant/size/shape、状态归属与组合、导航/校验/错误/焦点/键盘行为 |
| 内容与验收 | 正常内容和至少一种暴露布局弱点的样本、相关交互状态、适用视口/主题/语言、观察点及证据方式 |

“使用 React + Tailwind”“保持美观”“与项目一致”均不足以构成设计。新页面或结构重写需有足以定位主要区域与交互的布局说明、草图或轻量原型，不强制设计工具或高保真稿。局部间距修改可以只写参照组件、目标空间关系和复验状态。

先设计工作流与空间关系，再选择装饰数值。操作型页面优先可见工作区和扫描效率；同类间距要一致，靠角元素要检查到相邻两条内边界的留白与圆角轮廓。不同关系不必全部使用相同数值，不为“高级感”扩大空白或搬入另一产品的外观。

设计审查在写对应前端代码前完成，是 ready 的语义部分。已有明确实施授权时，自主处理范围内可逆设计决定；只把影响产品范围、关键行为和风险的未决取舍交给用户，不增加逐像素审批。获准的隔离原型可用于比较方案，结论要回到设计，原型不等于正式交付。

## 3. 把设计和状态落实到初版

状态按维度选择：异步 idle/loading/success/error，内容 empty/nonempty/partial，权限 allowed/denied，操作 enabled/disabled/pending。验证本次真实存在且有风险的组合；静态组件不凭空增加 loading 或权限态。

沿用组件库、token、表单方案和语义元素，检查默认 variant 与调用侧覆盖后的最终呈现。提交避免重复操作，失败保留输入或已有结果；导航、筛选、分页是否同步 URL、返回是否保留，遵循项目行为与需求。

准备正常内容和能暴露弱点的样本，如相邻短行与多行、长文件名、长错误文案；定义可换行/截断及完整内容入口，不能用全局隐藏溢出来掩盖布局问题。悬停、焦点、选中、禁用、展开分别处理，控件有可读名称、焦点可见，弹层保持正确焦点管理。动效服务反馈并遵循 reduced-motion，不新增无需求的持久化或状态。

大数据场景先测量内存/渲染/交互，再决定虚拟化或 Canvas/WebGL 等方案，不把某项优化作为通用必选项。

## 4. 初版后实际渲染、审查、修复、复验

UI 任务验证计划应包含适用的功能检查与 `browser` / `manual` 类型的 required 渲染审查，可在一个检查内关联截图审阅和实际交互步骤。写明路由、样本、状态、视口与预期关系，不能只写“截个图”或把视觉打磨推迟到所有任务完成以后。

1. 按项目版本和命令启动开发/预览环境；先核对包管理器与锁文件版本，避免启动时升级依赖。只使用可控 fixture、请求拦截或获准测试账号构造延迟、失败、权限等状态，不对真实数据做故障注入。
2. 确认路由、数据、字体与目标状态就绪，设置实际视口、主题和语言，打开需要观察的菜单/Tooltip 等。截图须包含布局上下文；DOM 中有元素或固定等待结束都不能证明渲染就绪。
3. **切换到审查视角并亲自查看生成图**：方向（与参照是否一致、主任务是否清楚）→结构（层级、密度、工作区空间）→细节（对齐、靠角留白、圆角、基线、截断、真实浮层外框）→交互（真实操作、键盘、失败恢复、焦点及状态连续性）→适配（目标窗口中的换行、遮挡、滚动和主题）。必要时用 DOM/computed-style 测量补充判断；不能以测试断言代替看图。
4. 将发现记为“状态/位置 → 现象 → 原因 → 改动 → 复验”。先修方向与结构，再修局部细节；同源问题检查本次范围内其他实例，共享组件改动验证真实消费页及相关变体。
5. 每次修复后重新运行受影响检查并查看对应最终渲染结果，直到满足下面的结束条件。无问题时记录具体观察，无需为了凑两轮修改而制造改动。

截图/录屏、交互步骤和测量结果记录实际代码版本、环境、视口、状态与可定位证据路径。功能验证不能由一张静态截图替代，视觉验收也不能由构建、类型检查或元素存在断言替代。旧日志/旧截图不能证明最后一次修改的效果，源码变更需重新评估相关证据，即使 Spec 指纹未变。

## 5. 结束条件与受限环境

本次范围没有已知且能处理的视觉/交互缺陷，适用行为检查通过，最终截图已审阅且证据对应最终代码，才能完成 UI 任务。发现可修问题时继续修复；必要运行能力缺失时完成独立可验证部分，保留 required 为未运行，标待验证/阻塞并写解除条件。环境不足不是 na，缺陷无法处理也不能靠“已知问题”备注变成通过。

检查控制台新增问题；未改动的第三方警告或既有缺陷应记录基线和影响，按项目政策处理，不为零警告扩大范围。批次在集成版本上复核适用用户流程与跨页一致性，不能仅相加各任务状态。

按影响面取样：局部 Tooltip/间距问题检查相关长短内容、交互状态与窄边界；页面重写检查参照、主要流程、正常/边界内容及目标窗口；共享组件检查消费页与实际变体。不强制全站、全主题或所有状态的笛卡尔积，不为可逆 CSS 微调编写只匹配类名的测试。

结束前按项目规范清理本次启动的预览、前端服务和测试实例，保留用户原有进程。交付说明具体体验改善、证据与限制；无浏览器或未实际查看图片时不得声称完成视觉验收。
