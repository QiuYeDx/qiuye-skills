# 质量门：适用性、证据与限制

## 三类检查不要混为一谈

结构门：ID/引用、覆盖、依赖 DAG、状态、记录、批准摘要等可机械检查。
语义门：需求是否正确、设计是否可行、任务是否遗漏、所选验证是否足够，需 Agent/人审查。
运行门：在实际目标环境执行测试/浏览器/接口等，提供可定位证据。

check_spec.py 只负责第一类，部分字段只能检查“写了什么”，不能确认写的是真的。
它不运行命令、不判断日志里的结果、不验证用户身份、不检查 Git 祖先关系，也不证明实现符合设计。
批准和任务指纹是防止无意复用过期状态的变更检测，不是数字签名或反作弊系统。

## 按层验证

| 层 | 范围 |
| --- | --- |
| 任务 | 本次 AC、直接改动、必要正反例与局部回归；格式化/类型检查按实际影响选择 |
| 模块 | 关键状态、权限、组件/接口间交互、数据边界、适用断点 |
| 集成/发布 | 合并版本上的跨模块链路、真实服务、完整 CI、兼容性、迁移与恢复 |

一次 UI 微调不必重测全项目全部页面。大型项目每个小任务不必跑所有昂贵测试，但要记录实际策略并在集成层完成必要验证。
若全量 CI 是项目既有合并要求，不能以“本 Skill 按风险”为由跳过。

## 验证计划与 N/A

tasks.md 每条检查有稳定 V 编号、类型、required/na、可执行命令或步骤。
required 表示本任务宣布完成前必须通过。na 只用于确实不适用的检查，写业务/技术理由。
缺浏览器、服务器未启动、权限不够、测试太慢、不会跑测试，都不是 na 的理由；保持 required、记录未运行、标待验证/阻塞。
可以有“不运行浏览器：纯服务器函数无 UI”，不能有“不运行浏览器：当前 Agent 没有浏览器”。

任务 AC 逐条关联通过的 V；record 写版本、环境、实际结果及证据。
测试数据应可控、自建自清；不要通过修改真实业务环境制造空态、错误或无权限场景。

## 正反例与基线

bugfix 尽量用先失败后成功的同一回归测试证明修复；无法自动化时保留复现步骤和观察。
不要求每个接口具有所有种类的异常；按契约验证适用输入错误、访问策略、资源不存在、重复操作/并发与边界。
未改动的已知基线失败，写实际对比与影响，由项目合并政策处理；本次回归不能登记为基线来规避。

## 什么不算完成

生产路径用固定返回值/假数据/空按钮冒充功能；只构建通过就声称交互正常；只测 mock 就声称真实接口一致；只存在日志文件就声称所有 AC 通过。
测试夹具、开发态 mock、受控 feature flag、本来就对外提供示例数据的功能，都不应被一刀切删除。
现有 TODO 或日志语句是否阻断，取决于是否影响本次生产行为与项目规范；不要做全仓库无关清理。

## 批次验收

记录集成版本、环境、适用用户流程、实际结果、风险与确认来源。需要人工验收时保留待验收，Agent 不代签。
CLI 的 --stage done 只表示当前任务声明通过结构门，不会把批次自动改为 accepted。
accepted 还要求任务全部完成/已废弃、验收记录非空且批次指纹匹配；记录内容的真实性仍须审查。
