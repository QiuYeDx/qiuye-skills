# 质量门与完成定义

每个门都是「不满足就不进入下一阶段」。自检时逐条打勾，不满足的条目要么补齐，要么在文档「未决问题」中登记原因。

## 需求门（requirements.md / brd.md 完成后）

- [ ] 每条需求有唯一编号（`BR-xx` / `R-<MOD>-xx`）与一句话标题
- [ ] 每条 R 标注来源 BR（L）；每条 BR 至少被一条 R 覆盖
- [ ] 每条需求有优先级（P0 必须 / P1 应该 / P2 可以）
- [ ] 每条需求有可测的验收标准（AC），用「在 X 条件下，做 Y，看到 Z」或 Given/When/Then 表达
- [ ] 每条需求覆盖主流程与至少一条异常流程（空数据、无权限、网络失败、并发冲突、超限）
- [ ] 涉及 UI 的需求写明页面/入口；涉及数据的需求写明字段、类型、必填、范围、默认值、唯一性
- [ ] 「范围外」章节非空，明确本次不做什么
- [ ] 非功能需求有具体数字（响应时间、并发量、数据规模、兼容范围）
- [ ] 无模糊词；存在的每条假设都编号为 `A-xx`，未决问题编号为 `Q-xx`
- [ ] 用户角色与权限矩阵完整（谁能看、谁能改、谁能删）

## 设计门（design.md 完成后）

- [ ] 「代码落点」表列出本模块会新建/修改的真实目录与文件，符合项目现有分层与命名
- [ ] 数据模型：实体、字段（类型/必填/默认/约束/索引）、关系、迁移方式
- [ ] 状态机：所有有状态的实体列出状态、迁移条件、谁能触发、不可逆点
- [ ] 接口契约：每个接口有方法、路径、鉴权、请求/响应示例、错误码、幂等性、分页/排序/筛选参数
- [ ] 与 `module-common` 的契约一致；跨模块依赖只引用 common 声明的类型/接口/错误码
- [ ] 后端设计满足 `backend-quality.md`「设计阶段产出要求」
- [ ] 前端设计满足 `frontend-quality.md`「设计阶段产出要求」（涉及 UI 时）
- [ ] 错误处理映射：每个后端错误码对应前端展示方式与文案
- [ ] 需求追踪矩阵：每条 R 至少映射到一个设计元素（接口/页面/表/组件）
- [ ] 风险与决策记录：备选方案与放弃原因
- [ ] 测试策略：单测、接口测试、组件测试、端到端各覆盖什么

## 任务门（tasks.md / task-list-overall.md 完成后）

- [ ] 每个任务一个会话内可完成（经验：新建/修改 ≤8 个文件，或 ≤300 行有效变更）
- [ ] 每个任务有：目标、关联需求、依赖、涉及文件、实现要点、验收标准、测试要求
- [ ] 每条 R 至少被一个任务覆盖（跑 `check_spec.py` 验证）
- [ ] 任务顺序：先 common 契约 → 再最小端到端链路（一条主流程前后端打通）→ 再横向扩展 → 最后打磨
- [ ] 前端任务与后端任务通过接口契约解耦，可并行；契约未定的不得开前端任务
- [ ] 每个 UI 任务的验收标准包含「五态齐全 + 浏览器自检通过」
- [ ] 每个接口任务的验收标准包含「正反例请求通过 + 错误码符合契约」
- [ ] overall 中每个任务标注阶段与依赖，且状态与模块 tasks.md 一致

## 完成门（Definition of Done，每个任务标 `已完成` 前）

功能真实可用：

- [ ] 实现与 `design.md` 一致；偏离处已回写设计并在 record 中标注
- [ ] 任务「验收标准」逐条通过，并在 record 写明验证方式
- [ ] 生产路径无 TODO / FIXME / 占位组件 / mock 数据 / 示意实现 / `console.log` / `debugger`
- [ ] 异常路径已实现（不只是 happy path）

前端（涉及 UI 时）：

- [ ] `frontend-quality.md`「浏览器自检流程」全部通过
- [ ] 五态可在浏览器中实际触发并符合设计
- [ ] 文案符合语言约定，无占位文案

后端（涉及接口/数据时）：

- [ ] `backend-quality.md`「接口验证流程」全部通过
- [ ] 迁移可在干净环境执行；回滚方式已记录
- [ ] 权限与参数校验有反例测试

测试与构建：

- [ ] 任务「测试要求」中的测试已添加并通过
- [ ] 项目 lint / typecheck / build 通过（或记录无法运行的原因）
- [ ] 未破坏既有测试

文档：

- [ ] `tasks.md` 该任务行：状态、完成日期、实施记录路径已填
- [ ] `task-list-overall.md` 对应行同步（L）
- [ ] `records/` 已有本任务记录
- [ ] 若接口/数据结构变化：`design.md` 与 `module-common` 已更新
- [ ] 无范围外改动；确有必要的已在 `changes/` 登记

## 放飞自我反模式（出现任一条即停下修正）

| 反模式 | 表现 | 正确做法 |
| --- | --- | --- |
| 自造需求 | 文档没写却「顺手」加了功能/字段/页面 | 登记 `A-xx` 或走变更管理 |
| 降级交付 | 「简化版」「示意」「后续完善」「先用假数据」 | 做真实实现；做不完就拆任务并标 `进行中` |
| 只做 happy path | 空态/错误/无权限没处理 | 按需求的异常流程逐条实现 |
| 跨模块乱改 | 为了跑通改了别的模块或 common | 停下，走变更管理 |
| 一口气领太多 | 一次会话改十几个文件跨多个任务 | 一次一个任务 |
| 跳过检查点 | CP 未确认就写业务代码 | 只读调研，等待确认 |
| 乐观状态 | 没验证就标 `已完成` | 标 `进行中` 并写清缺什么 |
| 静默偏离设计 | 实现和 design 不一致但不改文档 | 先改设计再改代码 |
| 前端不看效果 | 没启动浏览器就交付 UI | 执行浏览器自检流程 |
| 契约漂移 | 前端自己猜接口字段 | 以 common/design 契约为准，缺则先补契约 |
| 文档和代码打架 | record 说完成，代码里是 TODO | 收尾清单逐条核对 |

## 文档写作规范（把读者当零上下文的新人）

- 用具体值：字段类型、长度、范围、默认值、枚举全部值、示例数据
- 用具体行为：每个按钮点击后发生什么；每个异常用户看到什么文案、能做什么
- 用具体位置：页面路由、入口按钮位置、接口路径、表名、文件路径
- 一条需求只说一件事；能拆就拆
- 表格优先于长段落；流程用编号步骤
- 禁用模糊词：等等、类似、合理、适当、若干、友好提示、尽量、后续完善、大概、之类、必要时
- 不写「参考现有实现」而不指出具体文件
- 每处不确定的地方都用 `A-xx` / `Q-xx` 标出，不用「可能」「或许」
- 中英文术语首次出现时给出对照，之后全篇统一
