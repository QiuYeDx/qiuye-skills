# 执行、变更与恢复

## 真实授权与检查点

S 的明确实施请求通常足以授权范围内的低风险修改，不再人为增加文档审批。
M 默认把需求与当前设计/任务合并确认一次。L 先确认业务边界，再确认每个当前增量。
用户明确要求“按此范围直接做，细节自行决定”时可用 delegated，保留原话或可定位来源；不能把 Agent 的计划宣告当作用户同意。
high 风险需要具体批准 approved。发布、删除数据、外发信息等操作还要遵守宿主和项目的独立授权要求；Skill 批准不是全局豁免。

spec.json 的 approval 只描述当前需求范围的许可。设计中发现权限、安全、兼容或不可逆风险变化，先更新 risk/需求约束，使原批准失效，再确认。
局部内部实现调整、不改变既有 AC 的文件位置修正，可同步设计与写集并记录，不反复让用户审批内部细节。
检查 ready 不要求尚未发生的批准；实施前用 --require-approval。已经开始/完成的任务会自动触发批准检查。

## 按改动语义分类，不看提交前缀

| 分类 | 处理 |
| --- | --- |
| bugfix | 正确 AC 与实现不符：复现→先补可复现回归验证→修实现→验证。不必修改需求或升 BRD 版本 |
| internal-change | 用户行为不变：更新必要设计、验证兼容与性能风险。不改变 AC |
| behavior-change | 新增/改变外部可观察行为：明确旧→新→更新需求→确认影响→实现 |
| spec-correction | 原文有错/矛盾/缺失：记录证据和来源，显式纠正规格，重审受影响批准与验证 |

“修复体验”可能实为行为变更；“重构”也可能改变兼容性。不能只按 feat/fix 名称决定是否审批。
简单 bug 不强制新增 change.md；已有追踪时把问题与原 AC、任务、record 连起来即可。重大语义变化用 change 模板保存决策依据。
发现旧有测试失败，先区分已知基线问题和本次回归。记录命令、失败项与基线比较；不能靠删除测试或调低预期完成交付。

## 开始一个任务

读需求来源、当前 AC、相关设计元素和当前任务。阅读与任务有关的代码、契约和项目坑位；不重读所有历史记录。
检查分支/工作树与未提交 diff，不执行破坏性 reset/clean。
依赖需同时满足“任务自身验证已完成”和“其实现已在本工作基线可用”。填写依赖确认：依赖 ID、提交或工作树快照、实际核验方式。
共享写路径先协调。项目级格式化、依赖升级、公共组件 API 变化不能当作局部“顺手整理”。

## 状态语义

| 状态 | 意义 |
| --- | --- |
| 未开始 | 尚未领取或尚未动手 |
| 进行中 | 正在实现或验证 |
| 待验证 | 实现已到可交付状态，但必要运行/浏览器/接口/人工验证仍缺失 |
| 阻塞 | 存在明确依赖、环境、授权或需求障碍，记录障碍与解除条件 |
| 已完成 | 该任务 AC 和 required 检查通过，record 完整且与当前任务/AC 指纹一致 |
| 废弃 | 不再执行；不能继续给有效需求凑覆盖率，也不能成为有效任务依赖 |

待验证不是“差不多完成”的绿色状态。已完成不表示已合并；集成版本另记在任务字段。整体是否 accepted 由批次记录决定。
状态不是审批事件。若新问题推翻证据，把任务退回进行中/待验证，保留旧记录历史再执行；不得直接涂改旧结果来隐藏失败。

## 完成与后续增量

记录具体改动、实际版本（提交 SHA；有未提交修改时附工作树/补丁指纹）、验证环境、执行输出和未执行项。
本分支通过后，集成负责人在合并结果上做适用的集成验证；不能把同一份局部日志复用成端到端验证。
历史已完成任务/AC 尽量保持不变。新的产品行为创建新需求/新任务引用旧版本，避免重写历史证据。
下一批次选择 spec.json 已声明的新 ID，细化 deferred 内容并激活；当前批次切换不表示旧批次自动验收。

## 交接

只留下：当前任务、代码基线和未提交改动、必要入口、已执行证据、未验证/阻塞项、下一可执行动作。
已有 tasks/record 可定位时不用复制整张表。恢复会话先核对文档和代码是否仍一致，不能只凭“上一轮说完成”继续。
